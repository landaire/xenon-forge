# xbox360-sys

Raw bindings to the Xbox 360 kernel (`xboxkrnl.exe`) and XAM (`xam.xex`) for Rust code built for the `powerpc-unknown-xbox360` target.

## tl;dr

- Call kernel and XAM exports by ordinal from `no_std` titles, system modules, and the standard library.
- Imports are `unsafe` functions. The few that cannot break memory safety are safe.
- Export your own functions by ordinal, and hand entry points and callbacks to the kernel with the register state it expects.
- Use the interlocked operations that the devkit kernel loader accepts.
- Pass and read typed values: enums for closed argument sets, flag types for bit fields, newtypes for handles, statuses and results, and storage types for kernel objects.
- Share the types and `status` with host code. They compile on every target.

## Usage

```toml
[target.'cfg(target_os = "xbox360")'.dependencies]
xbox360-sys = "0.2"
```

Call an import in an `unsafe` block, and state why the arguments meet the requirements of the export:

```rust,ignore
// SAFETY: the format is a NUL-terminated string without conversions.
unsafe { xbox360_sys::xboxkrnl::DbgPrint(c"hello from rust\n".as_ptr().cast()) };
```

A few imports, such as `KeQueryPerformanceFrequency`, are declared safe, and you call them without `unsafe`:

```rust,ignore
let frequency = xbox360_sys::xboxkrnl::KeQueryPerformanceFrequency();
```

Arguments and results are typed:

```rust,ignore
use xbox360_sys::xboxkrnl::{self, Handle, ProcessorMode};

// SAFETY: `handle` is an open event handle that this code owns.
let status = unsafe { xboxkrnl::NtWaitForSingleObjectEx(handle, ProcessorMode::User, false, core::ptr::null()) };
status.result()?;
```

Kernel objects that you allocate, such as events, timers and critical sections, have storage types. Keep the storage at one address while the kernel uses it:

```rust,ignore
use xbox360_sys::xboxkrnl::{self, EventType, Kevent};

static DONE: Kevent = Kevent::new();

// SAFETY: `DONE` is static storage of the size of a KEVENT.
unsafe { xboxkrnl::KeInitializeEvent(DONE.as_ptr(), EventType::Notification, false) };
```

Read a data import, such as `XboxHardwareInfo`, through its typed view. `get` returns `None` when the loader did not resolve the import, as Xenia does for exports it lacks:

```rust,ignore
use core::sync::atomic::Ordering;

if let Some(info) = xbox360_sys::xboxkrnl::XboxHardwareInfo.get() {
    let flags = info.flags.load(Ordering::Relaxed);
}
```

The C declarations of every import are in `ffi`, generated by bindgen from the headers of the SDK in `src/sdk/include/xbox360`. They take the C types, and variadic imports take their extra arguments directly:

```rust,ignore
// SAFETY: the format takes one string, and `name` is NUL-terminated.
unsafe { xbox360_sys::ffi::DbgPrint(c"hello %s\n".as_ptr(), name.as_ptr()) };
```

To add an import, declare it in a header of the SDK and regenerate (see below). Write `DECLSPEC_NORETURN` when the export does not return:

```c
/** Closes a handle. */
XBOXKRNL_IMPORT(0x0CF) NTSTATUS NtClose(HANDLE Handle);
```

Code that the kernel or another module calls uses the console ABI, which expects the full 64-bit nonvolatile registers back. Wrap it with `bridged!`, or export it with `export!`:

```rust,ignore
extern "C" fn worker(context: u32) -> u32 {
    0
}

xbox360_sys::bridged!(pub worker_entry, worker);
xbox360_sys::export!(1, worker);
```

Pass `worker_entry`, not `worker`, to `ExCreateThread` with `xapi_thread_startup` 0. When `worker` returns, the kernel ends the thread with the returned value as its exit code.

The crate needs [xex-link](https://github.com/landaire/rust-xbox360) to turn the import and export records into the XEX import and export tables. Imports, the functions of `processor`, `mmio`, `interlocked` and `entry_bridge` exist only for `target_os = "xbox360"`. On other targets the crate has the types, the constants, the structure layouts and `status`, so host code can share them.

## The SDK and the thunk library

The headers in `src/sdk/include/xbox360` are the source of truth. C and C++ titles list `//src/sdk:xbox360` in `deps` and include `<xbox360/xboxkrnl.h>` and `<xbox360/xam.h>`. `src/tools/xbox360-bindgen` generates from the headers:

- `src/ffi.rs` of this crate, through bindgen.
- The thunk library `src/sdk/thunks/ppc32.S` and `ppc64.S`: one invocation per import of the macros in `src/sdk/thunks/macros.inc`, which define a function under each function import's own name and a slot `__imp_<name>` for each data import. This crate assembles it, and C titles link it.

The crate reads the thunk library from `src/sdk`, so it builds only inside this repository.

Regenerate after changing a header, and check that the outputs are current:

```sh
cargo run --manifest-path src/tools/xbox360-bindgen/Cargo.toml
cargo run --manifest-path src/tools/xbox360-bindgen/Cargo.toml -- --check
```

The typed declarations of `xboxkrnl` and `xam` link to the same functions. At compile time each one is checked against its C declaration: the same argument count, and for each argument and the result the same class (no value, 4 bytes or less, or 8 bytes). The check cannot tell an integer from a floating-point value of the same size.

## Why the stubs exist

Console code stores r3-r10 into the caller's frame before using them. The SysV frames that the powerpc code generation emits do not reserve that area, so there each import is a small stub that allocates it. Without the stub, a kernel call can overwrite the caller's saved registers on hardware. Xenia does not show the problem. The stub also moves the arguments where the two conventions differ: SysV passes a 64-bit argument in a register pair and the ninth argument at sp+8, while the console expects the 64-bit value in one register, the ninth argument at sp+0x50, and reserves an argument register for each floating-point argument.

The powerpc64 ILP32 code generation follows the console convention, so there each import is the thunk itself.

## Types

Every type in an import signature passes like the C integer of its width. Enums are `#[repr(u32)]` (or the C width), and the other types are `#[repr(transparent)]` newtypes.

Values the kernel returns are newtypes, never enums, so an unknown value is not undefined behaviour. NTSTATUS results are `NtStatus`, and Win32 error results are `Win32ErrorCode`. `BOOL` results are `Boolean`, and `BOOLEAN` results are `Boolean8`, which reads only the low byte.

Enums that name only part of the values the kernel accepts are `#[non_exhaustive]`. So is `KernelError`.

Flag types keep bits without a name only through `from_bits_retain`. `from_bits` rejects them. Enums convert from integers through `from_raw` or `TryFrom`.
